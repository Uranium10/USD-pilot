U.S.D 팀은 생성형 AI를 게임 규칙의 대체물이 아니라 반복 가능한 내러티브 제작 도구로 활용하고, 실제 플레이의 판단과 결과는 명시적인 코드로 보장하는 것을 목표로 한다. 기획, 프로그래밍, UI·연출, 데이터 검증을 긴밀하게 연결해 짧은 파일럿 안에서도 완결된 플레이 흐름을 구현했다.

※ 본 문서는 실제 팀원 정보가 저장소에서 확인되지 않아 역할 템플릿 중심으로 작성한 초안이다. 2인 이상 팀일 경우 아래 표를 실제 담당 내역에 맞게 수정해야 한다. 개인 참가라면 공모전 양식상 팀 소개 문서 제출 필요 여부를 확인한다.

## 2. 팀원별 역할

| 팀원 | 주요 담당 | 세부 업무 | 기여 산출물 |
|---|---|---|---|
| [팀원 1 / 대표] | 기획·디렉팅 | 핵심 루프, 부채·시장·야간 활동 설계, 세계관, 밸런스 의사결정, 플레이 테스트 총괄 | 기획 문서, 밸런스 기준, 스토리 방향, 최종 빌드 검수 |
| [팀원 2] | 클라이언트·UI | React 화면, Canvas 차트, 대화·튜토리얼, 오디오·볼륨 UI, 반응형 화면 및 접근성 | 게임 클라이언트, UI 컴포넌트, 시각·음향 연출 |
| [팀원 3] | 서버·AI 시스템 | Vercel Functions, Turso 저장, RunPlan·CycleScenario 파이프라인, 구조화 출력, 비용 최적화 | AI 시장 API, DB 스키마, 생성·복구 로직 |
| [팀원 4] | 콘텐츠·QA | 뉴스·소문·야간 활동·엔딩 콘텐츠, 회귀 테스트, 플레이 피드백 정리 | 콘텐츠 데이터, 테스트 시나리오, 제출 자료 |

팀원이 한 사람이 여러 영역을 담당했다면 행을 합치고 실제 기여율을 기입한다. 사용하지 않은 행은 삭제한다.

## 3. 협업 방식

### 문서 중심 요구사항 관리

게임의 하루 구조, 상환 주기, 시장 종료 조건과 같은 핵심 규칙을 문서에 먼저 명시하고 구현과 문서가 달라질 때마다 수정했다. 특히 ‘낮은 8분, 밤은 플레이어가 종료할 때까지, 상환 주기는 7일’처럼 플레이 경험을 좌우하는 기준은 코드 상수와 테스트에서 함께 검증했다.

### 작은 단위 구현과 반복 검증

기능을 한 번에 완성하기보다 정보 거래, 차트, 야간 활동, 채굴, 저장, 스토리 순서로 나누어 구현했다. 각 단계에서 실제 화면과 요구사항을 대조하고 플레이 피드백을 반영했다. UI 오류나 저장 불일치처럼 시연에 치명적인 문제를 우선 수정했다.

### AI 제안에 대한 사람의 최종 판단

복수의 AI 도구를 기획 검토와 구현 보조에 활용했으나 제안 간 충돌이나 잘못된 가정이 자주 발생할 수 있음을 전제로 했다. 모든 변경은 저장소 diff, 자동 테스트, 실제 API 호출 결과와 플레이 화면을 통해 확인한 뒤 반영했다. 비용 절감 실험 역시 측정 결과가 나쁜 병렬 방식은 적용하지 않았다.

## 4. 팀의 강점

1. **기획과 기술의 연결**: 부채 압박, 정보 비대칭, 낮·밤 리듬이 각각 독립 기능이 아니라 하나의 경제 루프로 작동한다.
2. **검증 가능한 AI 활용**: AI 출력 범위와 코드 판정 범위를 분리하고 비용·속도·실패 조건을 수치로 기록했다.
3. **시연 안정성 우선**: 서버 장애 시 로컬 시장 전환, 브라우저·DB 이중 저장, 반복 재시작 보호 등 파일럿 운영 상황을 고려했다.
4. **피드백 기반 개선**: 팀원 및 테스트 참여자의 차트, 뉴스 정합성, 음량, 저장 문제 제보를 기능 개선으로 연결했다.
5. **확장 가능한 데이터 구조**: 기업, 정보, 야간 활동, 주간 제약과 엔딩을 데이터 중심으로 관리해 이후 콘텐츠 추가가 용이하다.

## 5. 개발 도구 및 기술 스택

- 프론트엔드: React, Vite, Zustand, Canvas API
- 백엔드: Vercel Functions, Node.js
- 데이터베이스: Turso(libSQL)
- 생성형 AI API: Anthropic, OpenAI, Google GenAI 실험 경로
- 품질 관리: oxlint, Vite production build, Node 기반 회귀·통합 검사
- 형상 관리: Git, GitHub
