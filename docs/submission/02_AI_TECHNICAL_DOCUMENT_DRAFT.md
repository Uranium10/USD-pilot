## 1. 문서 요약

U.S.D는 AI가 만든 문장을 화면에 붙이는 게임이 아니라, **AI가 한 런의 사건 구조와 매주 거래 판단에 필요한 뉴스·정보를 설계하는 게임**이다.

런타임 AI는 다음 원칙으로 구성했다.

1. 중요한 전체 서사는 강한 모델로 미리 생성하고 풀에 저장한다.
2. 매주 필요한 시나리오는 비용과 속도가 낮은 모델로 생성한다.
3. 가격 경로는 결정론적 로직이 담당하고 AI는 의미 있는 사건을 결합한다.
4. 모든 AI 출력은 구조화된 JSON으로 받고 서버에서 다시 검증한다.
5. 다음 주 AI 시나리오는 현재 주가 시작될 때 미리 생성해 플레이 중 대기를 숨긴다.
6. 외부 AI가 실패해도 로컬 생성기로 게임을 계속할 수 있다.

현재 운영 설정은 전체 서사 `claude-opus-5 high`, 주간 시나리오 `gpt-5.6-luna low`다. `gemini-3.6-flash`는 짧은 보조 텍스트와 실험 경로를 위해 구현되어 있다.

### 핵심 주장

> **생성형 AI의 다음 단계는 더 많은 콘텐츠를 만드는 것이 아니라, 플레이어가 다음에 마주할 조건을 설계하는 것이다.**

U.S.D에서 AI는 다음 세 역할을 맡는다.

1. **Director:** 7주 전체의 갈등과 매주 일어날 사건을 연출한다.
2. **System Input:** 사건을 종목·방향·크기·시점·정보로 구조화해 게임 엔진에 전달한다.
3. **Persistent World:** 이전 주의 미해결 사건을 다음 주 입력으로 넘겨 한 판의 연속성을 만든다.

가격 계산과 거래 판정은 AI에 맡기지 않는다. 결정론적 엔진이 게임 규칙을 지키고 AI가 그 규칙 안에서 의미 있는 변주를 설계한다. 이 결합이 단순 텍스트 생성과 U.S.D의 AI Director 구조를 구분한다.

### 기술과 플레이의 직접 연결

런타임 AI는 세계관 속 특정 AI 캐릭터를 연기하지 않는다. 그 역할은 시장 사건과 정보 비대칭을 만드는 게임 시스템이다.

- **시스템:** RunPlan과 CycleScenario가 매 판의 시장 서사를 연출한다.
- **정보:** 같은 사건을 사전 정보와 장중 뉴스로 나눠 제공한다.
- **플레이:** 플레이어는 정보 구매, 매수·매도와 자원 배분으로 대응한다.

따라서 제출에서 강조할 지점은 배경 설정과 런타임 모델의 메타적 연결이 아니라, AI 출력이 실제 거래 규칙과 플레이 선택으로 이어진다는 구현이다.

## 2. AI가 해결하는 문제

### 2.1 반복 플레이의 서사 반복

고정 뉴스만 사용하면 두 번째 플레이부터 정답을 외울 수 있다. U.S.D는 런마다 다른 사건 아크와 주간 뉴스·정보를 생성해 같은 경제 규칙 안에서도 다른 판단을 요구한다.

### 2.2 랜덤 가격과 이야기의 분리

가격만 무작위로 움직이고 뉴스가 장식으로 붙으면 플레이어는 정보를 읽을 이유가 없다. U.S.D의 사건에는 다음 구조가 포함된다.

- 영향받는 종목
- 상승/하락 방향
- 영향 크기
- 발생 시점
- 플레이어에게 보이는 뉴스
- 같은 사건을 미리 암시하는 정보

서버가 이 구조를 가격 경로에 합성하므로 뉴스와 정보가 실제 거래 판단에 연결된다.

### 2.3 생성 지연으로 인한 실시간 플레이 중단

주간 시나리오 생성은 실측상 약 15~25초가 걸린다. 이를 장 시작 시 기다리게 하면 실시간 게임의 리듬이 끊긴다. 그래서 AI 시나리오와 결정론적 가격 시장을 분리하고 다음 주 시나리오만 약 56분 전에 미리 생성한다.

### 2.4 AI 데모와 실제 게임 사이의 간극

AI 데모는 한 번 멋진 결과를 보여 주면 성공할 수 있지만 게임은 수십 번의 호출 중 한 번만 깨져도 플레이 경험이 무너진다. U.S.D는 다음 조건을 처음부터 제품 요구사항으로 취급했다.

- 응답 지연이 실시간 입력을 막지 않을 것
- 사용자별 서사가 섞이지 않을 것
- 뉴스와 정보가 실제 가격 사건에 연결될 것
- 잘못된 구조와 문장을 자동으로 검출할 것
- 외부 API 장애에도 게임이 진행될 것
- 한 판의 비용이 반복 플레이 가능한 수준일 것

이 때문에 모델 자체보다 프리페치·영속 상태·검증·재시도·fallback을 AI 기술의 핵심으로 보았다.


## 4. 모델 역할 분리

### 4.1 Narrative: Claude Opus 5 high

RunPlan은 7주 전체의 굵은 인과관계를 정한다. 매주 호출하지 않고 미리 생성한 뒤 `run_plan_pool`에 저장한다.

선정 이유:

- 긴 범위의 사건 인과와 복선 회수 품질이 중요하다.
- 플레이어 요청 경로에서 생성하지 않으므로 속도보다 품질을 우선할 수 있다.
- 한 RunPlan을 여러 세션에서 재사용해 고비용 호출을 분산할 수 있다.
- 손상된 결과는 `arcs`, `theme`, `worldTone`, 종목 연결을 검사하고 최대 3회 재시도한다.

운영 방식:

- 일반 플레이는 풀에서 RunPlan을 읽으므로 판당 즉시 생성 비용이 없다.
- 풀 보충은 배치 API를 이용할 수 있다.
- RunPlan은 실제 기업명이 아니라 `stock-1~5` 슬롯을 사용해 다른 기업 조합에도 재사용한다.

### 4.2 Weekly: GPT-5.6 Luna low

CycleScenario는 현재 주에 활성화된 RunPlan 아크와 이전 `worldState`를 받아 7일치 시나리오를 만든다.

현재 출력의 핵심 필드:

```json
{
  "cycle": 3,
  "title": "주간 시나리오 제목",
  "days": [
    {
      "day": 1,
      "events": [
        {
          "eventId": "event-id",
          "primaryStockId": "stock-2",
          "direction": "down",
          "magnitude": "major",
          "impactProgress": 0.55,
          "headline": "플레이어에게 표시되는 완결된 뉴스 문장."
        }
      ],
      "rumorSeeds": [
        {
          "targetEventId": "event-id",
          "sourceArchetype": "worker",
          "confidence": "medium",
          "angle": "같은 날 사건을 예고하는 정보 문장."
        }
      ]
    }
  ],
  "nextWorldState": {
    "tensions": [],
    "unresolvedEvents": [],
    "companyFlags": []
  },
  "selfCheck": {
    "consistentWithRunPlan": true
  }
}
```

Luna low 선정 이유:

- 같은 RunPlan 2개를 1→7주차로 이어간 라이브 경로 14회 실측에서 14/14 검증을 통과했다.
- Terra medium 대비 비용 58.0%, 시간 30.6%를 줄였다.
- 사건 191개와 정보 182개에서 orphan rumor와 주체 불일치가 발견되지 않았다.
- 런당 주간 GPT 비용은 약 `$0.1197`로 측정됐다.

### 4.3 Filler: Gemini 3.6 Flash

짧은 소문 플레이버, 필드 단위 복구처럼 4줄 이내의 저위험 보조 텍스트를 위한 경로다. 날짜별 본문을 Gemini로 병렬 생성하는 실험도 구현했지만, 503 재시도와 호출 오버헤드 때문에 주간 운영 경로에는 채택하지 않았다.

**운영 모델과 실험 모델을 문서에서 분리하는 이유:** 벤치마크용 Gemini 3.5 Flash-Lite 초안·수정 실험은 비용 가능성을 확인한 연구 결과이며 현재 플레이어 요청 경로에는 연결하지 않았다.

## 5. 생성 파이프라인

### 5.1 런 시작

1. 세션별 `deviceId`를 확인한다.
2. 저장된 RunPlan이 없으면 `run_plan_pool`에서 무작위로 하나를 선택한다.
3. 실제 런에서 뽑힌 5개 기업 ID·이름·업종 매핑을 주간 모델에 전달한다.
4. 1주차 시나리오를 생성하거나 재시작 보호 캐시를 사용한다.

### 5.2 주간 생성

1. 현재 cycle에 활성화된 RunPlan 아크를 추린다.
2. 이전 주의 미해결 사건과 기업 상태를 `worldState`로 제공한다.
3. 모델이 JSON Schema에 맞는 7일치 사건과 정보를 생성한다.
4. 서버가 문장·연결·주체를 검증한다.
5. 통과하면 다음 `worldState`와 시나리오를 주차별 저장소에 기록한다.
6. 결정론적 가격 시장과 AI 시나리오를 합성한다.

### 5.3 다음 주 프리페치

주 시작 시 다음 주의 AI 시나리오만 비동기로 생성한다.

- AI 시나리오는 플레이어의 마지막 코인 가격에 의존하지 않는다.
- 가격 시장은 다음 주 도달 시 실제 직전 종가를 받아 즉시 생성한다.
- 두 결과는 그 시점에 합성된다.
- 프리페치 창은 정산 화면의 수 초가 아니라 7일 × 8분, 약 56분이다.
- 캐시가 있으면 AI를 다시 호출하지 않는다.

이 구조로 실측한 프리페치는 최초 약 19.5초, 실제 주차 도달 시 약 0.1초였다.

## 6. 프롬프트 설계

### 6.1 RunPlan 프롬프트 목표

- 7주 동안 시작·확대·회수되는 사건 아크 설계
- 특정 회사 이름 대신 재사용 가능한 종목 슬롯 사용
- 복선 시작 주차와 결말 주차 분리
- 시장 사건이 단순 선악 구도가 되지 않도록 이해관계 충돌 포함
- 7주차에는 남은 아크를 회수하고 에필로그로 마무리
- 어조와 갈등축을 매 생성마다 바꿔 풀의 다양성 확보

요약 예시:

```text
7주 전체에 걸친 시장 서사 계획을 작성한다.
각 아크는 관련 stock ID, 복선 시작 주차, 본격 시작 주차,
결말 주차와 플레이어가 관찰할 수 있는 시장 결과를 가진다.
7주차에는 새 장기 떡밥을 만들지 말고 기존 아크를 회수한다.
```

### 6.2 CycleScenario 프롬프트 목표

- 실제 기업명·업종과 `stock-1~5` 매핑 준수
- 뉴스에 구체적인 주체·행동·결과 포함
- 내부 ID를 플레이어 문장에 노출하지 않음
- 한국어 완결 문장 사용, 생략부호와 손상 표식 금지
- 매일 최소 한 개의 사건과 같은 날 사건을 가리키는 정보 생성
- 정보는 사건을 그대로 정답처럼 말하지 않고 출처와 관점을 가짐
- 7주차도 같은 주에 해소되는 정보는 정상적으로 생성

요약 예시:

```text
이번 주의 활성 아크와 이전 worldState를 바탕으로 7일치 시장 사건을 작성한다.
headline과 angle은 실제 기업명을 사용할 수 있으며 자연스러운 한국어 완결 문장이어야 한다.
각 rumorSeed.targetEventId는 반드시 같은 day의 eventId를 참조한다.
기업이 업종과 무관한 행위의 직접 주체가 되지 않게 한다.
```

### 6.3 프롬프트에 넣지 않는 정보

- API 키와 인증 토큰
- 사용자의 개인정보
- 브라우저 저장 데이터 전체
- 거래 주문 내역처럼 시나리오 생성에 불필요한 플레이 상태

필요한 정보만 전달해 입력 토큰과 데이터 노출을 줄였다.

## 7. 구조화 출력과 검증

### 7.1 JSON Schema

자유 형식 텍스트를 파싱하지 않고 제공사별 구조화 출력 기능을 사용한다.

- OpenAI: `response_format: json_schema`, strict mode
- Anthropic: `output_config.format: json_schema`
- Gemini 실험: `responseJsonSchema`

구조화 출력은 JSON 문법과 필드 형태를 보장하지만 의미 품질까지 보장하지 않는다. 따라서 서버 검증이 별도로 필요하다.

### 7.2 서버 검증 항목

- 한국어 문장 존재 여부
- 지나치게 짧거나 긴 문장
- `stock-1` 같은 내부 ID 노출
- `...`, placeholder, corrupted 같은 손상 표식
- 매일 뉴스와 정보가 최소 한 개씩 존재하는지
- 정보가 같은 날 존재하는 eventId를 참조하는지
- 헤드라인이 자기 종목 대신 다른 상장사만 주체로 삼는지
- RunPlan과의 selfCheck 결과

### 7.3 재시도 정책

주간 생성은 최대 3회 시도한다.

1. 첫 결과가 무결하면 즉시 사용한다.
2. 결함이 있으면 다시 생성한다.
3. 세 번 모두 결함이 남으면 결함 수가 가장 적은 결과를 사용한다.

완전한 예외로 로컬 시장 전체가 대체되는 품질 절벽보다, 일부 결함이 있는 AI 서사를 유지하는 편이 낫다는 판단이다. 파싱 자체가 불가능하거나 응답이 비어 있을 때는 상위 fallback으로 전달한다.

## 8. AI와 결정론적 게임 로직의 경계

### AI가 결정하는 것

- 한 런의 사건 아크와 복선
- 주간 뉴스의 의미와 문장
- 어떤 종목이 사건의 영향을 받는지
- 상승/하락 방향과 영향 크기 등 시나리오 의도
- 다음 주로 이어질 미해결 상태

### 게임 코드가 결정하는 것

- 실제 가격 경로의 수치와 안전 범위
- 매수·매도 체결과 수수료
- 부채·이자·최소 상환액
- 채굴 생산량과 업그레이드 비용
- 정보 가격과 정확도 매핑
- 저장, 복원, 중복 호출 방지
- 엔딩 조건

이 경계는 AI가 잘못된 숫자를 생성해 경제 밸런스를 파괴하지 않게 하면서도, 사건의 의미와 반복 플레이 다양성은 AI가 담당하게 한다.

### AI Director의 제약이 곧 디자인이다

디렉터에게 자유가 필요하지만 제작 예산과 무대 규칙도 필요하다. U.S.D의 JSON Schema와 결정론적 엔진은 AI를 제한하는 장치인 동시에, 생성 결과를 실제 게임으로 바꾸는 연출 규칙이다.

- AI는 `방향=하락`, `영향=major`, `시점=0.55`를 제안한다.
- 엔진은 이를 허용된 가격 범위와 거래 규칙 안에서 실행한다.
- AI는 뉴스와 정보의 의미를 만든다.
- 검증기는 연결이 끊기거나 주체가 뒤바뀐 장면을 다시 생성하게 한다.

따라서 U.S.D의 AI는 무제한 채팅 모델이 아니라 **게임 규칙 안에서 연출하는 제약된 디렉터**다.

## 9. 비용과 지연 최적화

### 9.1 사용하지 않는 출력 필드 제거

초기 CycleScenario에는 화면과 게임 로직에서 소비하지 않는 필드가 많았다. 다음 필드를 슬림 스키마에서 제거했다.

- `openingNarration`
- `weeklyTheme`
- `marketMood`
- `companyStates`
- `dailyTheme`
- `relatedStockIds`
- `detail`
- `causeEventId`
- `selfCheck.notes`

동일 모델 실측에서 슬림 스키마는 생성시간 약 43.6%, 비용 약 43.9%, 출력 토큰 약 46.3%를 줄였다.

### 9.2 RunPlan 풀

가장 비싼 장기 서사는 플레이 도중 생성하지 않는다. 검증된 RunPlan을 공용 풀에 미리 채우고 런 시작 시 선택한다. 새 게임의 대기와 판당 Claude 비용을 제거했다.

### 9.3 Prompt caching과 상태 최소화

고정 시스템 프롬프트가 캐시되도록 메시지 순서를 유지한다. 각 주차에는 전체 과거 로그 대신 활성 아크와 압축된 `worldState`만 보낸다.

### 9.4 모델 비교 실험

같은 RunPlan id 81·90을 사용해 모델·effort를 비교했다.

| 후보 | 호출 조건 | 총시간 | 총비용 | 자동/정성 결과 | 판단 |
|---|---:|---:|---:|---|---|
| Terra medium | 14주 | 314.5초 | $0.5690 | 높은 문장 품질 | 기준 모델 |
| Luna low 라이브 경로 | 14주 | 218.2초 | $0.2388 | 14/14 무결함 | **운영 채택** |
| Gemini 3.6 Flash medium | 14주 | 210.0초 | $0.3731 | 업종 불일치, 낮은 사건 밀도 | 미채택 |
| Gemini 3.5 Flash-Lite minimal | 14주 | 90.7초 | $0.0805 | 매우 저렴하나 비문·업종 오류 | 미채택 |
| Flash-Lite 초안+의무 수정 | 28회 | 185.7초 | $0.1789 | 일부 오류 수정, 의미 오류 잔존 | 연구 후보 |

비용만 가장 낮은 모델을 선택하지 않았다. 사용자에게 직접 노출되는 뉴스의 의미 품질과 사건 연결 무결성을 함께 평가해 Luna low를 운영 모델로 결정했다.

## 10. 실패 대응과 안정성

### 세션별 AI 상태 분리

RunPlan과 worldState를 모듈 전역 변수에 두면 서버리스 인스턴스 재시작 때 사라지거나 서로 다른 사용자가 상태를 공유할 수 있다. 모든 상태를 `deviceId` 단위로 Turso에 저장해 세션 오염을 막았다.

### 주차별 입력 고정

각 cycle에 사용한 worldState를 별도 행으로 저장한다. 다음 주 프리페치가 먼저 실행되거나 요청 순서가 바뀌어도 이전 주 입력이 덮어써지지 않는다.

### 재시작 보호

반복 새로고침으로 같은 첫 주가 계속 유료 생성되는 것을 막기 위해 보호 캐시와 생성 횟수 제한을 둔다. 캐시 적중은 신규 생성 횟수로 세지 않는다.

### 로컬 fallback

외부 AI API와 DB가 실패해도 클라이언트가 결정론적 로컬 시장을 생성한다. AI 기능의 장애가 게임 전체 장애로 번지지 않는다.

## 11. 개발 과정의 생성형 AI 활용

런타임 AI 외에도 개발 과정에서 AI 코딩 도구를 사용했다.

| 도구 | 활용 범위 | 사람의 검증 방식 |
|---|---|---|
| OpenAI Codex | 코드베이스 분석, 기능 구현, 모델 벤치마크, 비용 계산, 문서화 | diff 검토, lint/build, 실 API 호출, 수치 재계산 |
| Anthropic Claude 계열 코딩 도구 | 아키텍처 검토, 저장·프리페치·검증 구조 개선, 실험 기록 | 동일 저장소 로그, 자동 검사, 프로덕션/로컬 경로 검증 |
| 런타임 LLM API | RunPlan과 CycleScenario 구조화 생성 | JSON Schema, 서버 검증, 재시도, fallback |

### AI 개발 도구 사용 원칙

- AI가 제안한 코드는 실행 전 기존 구조와 충돌 여부를 확인한다.
- 기능 수정 후 `npm run lint`, `npm run build`와 도메인 검증 스크립트를 실행한다.
- 모델 비용·속도 주장은 실제 API 호출의 usage와 공식 단가로 계산한다.
- 실패한 실험도 로그에 남겨 같은 접근을 반복하지 않는다.
- API 키와 `.env.local` 내용은 프롬프트·문서·저장소에 포함하지 않는다.

## 13. 한계와 향후 개선

### 의미 검증의 한계

현재 검증은 문장 형식, 종목 주체와 이벤트 연결을 잘 잡지만 "통신사가 치료제를 개발한다" 같은 업종 의미 오류를 완전히 판별하지 못한다. 향후에는 업종별 허용 역할 규칙이나 별도 경량 검증 모델을 도입할 수 있다.

### 스키마 추가 압축

현재도 `eventId`, `targetEventId`, `sourceArchetype`, `confidence`, `impactProgress`처럼 코드에서 결정할 수 있는 필드가 남아 있다. 사건과 정보를 한 객체로 묶고 메타데이터를 서버에서 생성하면 출력 비용을 더 줄일 수 있다.

### 관측성과 운영 지표

운영 배포 후 다음 지표를 집계할 계획이다.

- 주차별 생성 성공률과 재시도율
- 캐시 적중률
- 평균/95백분위 생성시간
- 주차·런당 토큰 비용
- fallback 발생률
- 검증 이슈 유형별 빈도

### 다음 단계: 플레이 스타일을 읽는 Director

현재 AI는 RunPlan과 서사 worldState를 바탕으로 다음 주를 설계하며, 플레이어의 개별 주문 내역을 직접 입력받지는 않는다. 향후에는 개인정보나 전체 거래 로그를 전송하지 않고도 다음과 같은 요약 지표만 활용할 수 있다.

- 위험 선호도 구간
- 정보 구매 성향
- 분산 투자/집중 투자 경향
- 야간 활동 선택 비율

이 요약을 안전한 게임 파라미터로 변환하면 AI Director가 플레이 스타일에 맞춰 정보 난이도와 사건 구성을 조절하는 다음 단계로 확장할 수 있다. 이는 현재 구현과 향후 비전을 명확히 구분한 제안이다.
